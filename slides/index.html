開場先問：有多少人曾經把檔名存成 final、final-2、真的-final？今天的目標就是用一套更可靠的方式取代它。

今天只完成一件事

把一個想法，
安全地送進團隊的正式版本。

你不需要背完所有指令。你需要知道自己在哪裡、改了什麼、下一步要保存什麼。

強調課程目標不是背誦。若時間有限，後面的進階指令可以略過，但三個核心問題要反覆詢問。

先拆掉第一個誤會

Git ≠ GitHub

🧰

Git

  • 你電腦上的版本控制工具
  • 離線也能 commit、branch、merge
  • 保存「內容如何演進」
+
🌐

GitHub

  • 放置 Git repository 的平台
  • 提供 Issue、PR、Review、Actions
  • 讓團隊討論與分享版本
類比：Git 像相機與相簿，GitHub 像可協作的雲端相簿。沒有 GitHub 仍能使用 Git。

每天最重要的循環

先看，再選，最後保存。

terminal
$ git status
$ git diff
$ git add menu.md
$ git diff --staged
$ git commit -m "Add cinnamon latte"

status → add → commit

不要把 `git add .` 當成反射動作。先確認這次版本真的只做一件事。

現場逐行執行。特別比較 git diff 與 git diff --staged；問學員 add 前後內容去了哪裡。

⌨️ 實操一｜8 分鐘

08:00

替咖啡館新增一杯「肉桂拿鐵」

  1. 修改 menu.md
  2. 用 status 與 diff 確認
  3. 只 add 這個檔案
  4. 寫一個「未來的你看得懂」的 commit

完成標誌：git status 顯示 working tree clean，最新 commit 訊息能說明新增了什麼。

讓兩人一組：Driver 操作，Navigator 在按 Enter 前預測結果。時間到交換一組 commit message，討論哪個比較容易理解。

犯錯不可怕，搞不清楚狀態才可怕

Git 是你的安全網

1

先看差異

git diff
先知道自己要丟掉什麼。

2

尚未提交

git restore file
復原工作區檔案。

3

已經分享

git revert ID
用新 commit 反轉錯誤。

共同歷史的原則：錯誤可以留下，來龍去脈要清楚。不要任意改寫隊友已經取得的 commit。

這裡先不教 reset。新手最需要的是能判斷 restore 與 revert 的使用時機，並養成先 diff 的習慣。

平行宇宙，但很輕量

Branch 讓未完成的工作，不打擾正式版本。

main A B C D
feature/cake E F

Branch 不是複製一整份專案；它是一個指向 commit、會跟著你前進的標籤。

指著圖說：A/B 是共同祖先，feature 有 E/F，main 繼續出現 C/D。兩條時間線可以稍後再整合。

新品秘密開發

建立 → 工作 → 回主線 → 合併

terminal
$ git switch -c feature/acorn-cake
# 修改、add、commit...

$ git switch main
$ git merge feature/acorn-cake
$ git branch -d feature/acorn-cake

合併的方向

先切到要接收改動的 branch，再 merge 要帶進來的 branch。

main ← feature

最常見錯誤是站錯 branch 合併。請全場一起說一次：先切到接收方，再 merge 來源方。

⌨️ 實操二｜10 分鐘

10:00

在秘密 branch 開發「橡實蛋糕」

  1. 建立 feature/acorn-cake
  2. 修改菜單並 commit
  3. 切回 main，觀察內容消失
  4. 合併後再觀察內容回來
內容消失時刻意停一下，讓學員說明為何不是檔案遺失。最後用 git log --oneline --graph --all 看歷史。

Conflict 不是錯誤，是一個決策點

⚡

  1. git status 找衝突檔
  2. 編輯成團隊真正想要的內容
  3. 移除三種衝突標記
  4. add ＋ commit
強調解衝突不是「選比較新的」，而是理解兩邊意圖後做內容決策。想退出可用 git merge --abort。

Issue 記錄為什麼，commit 記錄如何一步步做，PR 記錄整體變更與 review 決策。三層資訊彼此互補。

好的 PR 讓 Reviewer 很快進入狀況

不是「請幫我看」，而是提供一條驗證路徑

作者要說清楚

  • 為什麼要改？
  • 這次改了什麼？
  • 要怎麼驗證？
  • 有哪些取捨或未完成範圍？

Reviewer 要真的看

  • 先看 Files changed
  • 確認沒有無關檔案與秘密
  • 留言要具體、對事不對人
  • 問題處理後才 Approve
可以展示 repo 的 PR template。提醒學員：Review 是共同負責品質，不是找碴，也不是只按 Approve。

⌨️ 實操三｜12 分鐘

12:00

把學習筆記送進 Pull Request

  1. 建立 Issue 與 branch
  2. 新增一份個人學習筆記
  3. commit、push、建立 PR
  4. 和隔壁同學交換 Review

PR 內容加入 Closes #Issue編號，合併時就能自動關閉對應 Issue。

若只有一人，改做 self-review。要求至少一則具體建議，而不是只留言 LGTM。

五條救命原則

先停一下，通常比多打一個指令更快。

  • 🧭常看 status
    先確認 branch 與當前狀態。
  • 🔎復原前看 diff
    知道自己即將丟掉什麼。
  • 🧩一個 commit 一件事
    讓歷史容易理解與反轉。
  • 🔐秘密永遠不要 commit
    密碼與 token 放進環境變數。
  • 🚫共同分支別亂 force push
    已分享的歷史優先用 revert。
  • 🙋看不懂就先問
    不要貼上來路不明的破壞性指令。
特別提醒：把 secret 從最新 commit 刪除仍不代表它沒出現在歷史，外洩後要立刻撤銷並換新。

離開前，帶走三個問題

每次動手前，先問：

1

我在哪個 branch？

git status

2

我改了什麼？

git diff

3

下一個 commit 放什麼？

git diff --staged

請大家不看投影片，口頭回答三個問題分別用什麼指令。這比背更多進階指令重要。
